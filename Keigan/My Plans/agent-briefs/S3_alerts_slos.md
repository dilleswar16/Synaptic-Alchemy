## Backend (you own)
`controllers/alert_controller.py`, `alert_intake_controller.py`, `slo_controller.py` (stubs); `services/alert_service.py`, `slo_service.py` (skeletons: keep contract methods); `dtos/alert_dtos.py`, `slo_dtos.py`; `resources/catalogs/sli_catalog.yaml`; prompt `alert_group_title.md`; `ai/alert_ai_schemas.py`; seed `seed/alert_and_slo_seed.py` (`SEED_ORDER = 20`).

1. **Intake** (PUBLIC `POST /api/alerts/in/{alert_source_id}`): token in `X-Keigan-Token` or `?token=`, optional HMAC-SHA256 `X-Keigan-Signature`, constant-time compare against SHA-256 hash (incl. previous secret during rotation overlap), 256 KB limit, `rate_limiter`, store raw `alert_event`, enqueue `process_alert_event`, 202 fast, count auth failures.
2. **Alert sources:** CRUD, secret shown once, rotation (24 h overlap), pause, test (simulated payload through the pipeline), recent events (live listener), setup instructions with real values (Azure action group with common alert schema — CLI/PowerShell/Terraform/Portal; Elastic webhook connector + body template; generic canonical JSON), Azure alert-rule discovery (`azure_client.list_alert_rules` live; realistic simulated rules for simulated components).
3. **Mapping:** Azure common alert schema, Elastic, Generic (JSONPath via `read_json_path`, severity map, service map; suggestions via `list_json_paths`). Mask PII in summaries.
4. **Pipeline** (job `process_alert_event` + delayed job `settle_alert` via `available_at`): normalise → deduplicate (stable fingerprint, label-order independent) → lifecycle (resolve, flapping) → suppress (maintenance, mute, environment, severity) → settle → group (same service; dependency via `service_dependency`; same rule; open incident) → prioritise (weights, SLO burn boost, rare-rule boost) → decide (`InvestigationService(session).start_investigation(application_id, "alert_group", alert_group_id=…, service_ids=…)`, guarded: leave group queued with a clear reason; joined alerts → `attach_alerts_to_investigation`, guarded; rate limit) → notify (record decision; call S4 only if a suitable method exists). Every stage writes `alert_decision` with a human-readable reason and the Observe-mode "would have" outcome. Group titles via fast model with deterministic fallback + mock.
5. **Incident creation policy** (`incident_creation_policy_json`, edited via S1's PATCH): `suggest` → `servicenow_incident_suggested`; `automatic` → `IncidentService(session).create_servicenow_incident_from_alert_group` (guarded). `POST /alert-groups/{id}/create-servicenow-incident` (guarded, clear 501 if unavailable).
6. **Policy and views:** noise policy GET/PUT (defaults per sample plan), maintenance windows, mute rules (expiry + reason required), preview (re-run in memory over the last 7 days → funnel), funnel across applications, groups list/detail (members + decision log), feedback, weekly noise report (job `weekly_noise_report`), job `simulate_alerts_for_scenario` (turn a scenario window's `alert_rule_names` into Azure-common-schema events: repeats every 2–5 min, some flapping, resolved at the end, across primary and dependency services).
7. **SLOs:** catalogue per service type (incl. hardware, mainframe, SaaS rows from spec §6.10); proposals (job `measure_sli_proposals`: 30 days via telemetry gateway `sli_counts` / metrics; gate on data availability with disabled reasons; `statistics_utils` targets; latency thresholds; budget minutes; headline SLO on the entry point; supporting signals); accept (one click); SLI/SLO CRUD incl. custom SLI; backfill (job `backfill_sli`, bulk insert); collection every 5 min (job `collect_due_measurements`); burn rates (job `evaluate_burn_rates`: 14.4× 1 h & 5 min = page, 6× 6 h & 30 min = ticket → `slo_burn_alert` + an internal alert through your pipeline via an auto-created `keigan_slo` source + `NotificationService(session).notify_slo_burn_alert` guarded); `/slo-dashboard`; series with target + burn-down; ecosystem heatmap; contract `summarize_slos(application_ids)` (aggregate in SQL — used by home, investigations, intelligence).
8. **Seed** (idempotent): alert sources per app (Azure Monitor; Elastic for CHAD; one Generic), noise policy (CLMJP active, others observe), a maintenance window and a mute rule, historical alerts for each `seed_context.historical_scenarios` window run through the real pipeline, SLIs/SLOs for every app accepted from proposals with 30-day backfill (fast bulk insert).
